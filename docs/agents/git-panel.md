# `git-panel`

Notes for agents on the mod in `packages/git-panel/mods/git-panel/`. The index and what holds for every mod are in `AGENTS.override.md`.

The Git Panel replaces Herdr's `changes` view. Its gallery title and panel heading both read Git Panel. It shows commit history as a graph, branches, remotes, tags, stashes and uncommitted changes, with actions for day-to-day Git work.

## What is where

- `main.js`: the panel. `refresh()` and `read()` read the repository, and the log again only when `stamp` changed; `history()` makes the graph's rows; `nearEnd()` says the graph is scrolled to within a screen of its end and `loadMore()` reads the next page of the log, once; `graph()`, `graphRow()` and `cell()` draw them; `refs()` is the other view; `detail()`, `work()` and `changed()` are the lower half; `act()` runs a request; `show()` asks the tab's `git-diff` pane for a file and `edit()` its editor; `visible()` says whether the panel is on screen; `survey()` finds the folder's other repositories and `choose()` shows one; `peek()` reads how each stands (branch, files changed, ahead, behind: `stands()`) and `states()` adds the one shown, for the strip under the header (`chip()`, up to `STRIP_MOST` repositories) and the header's list (`menu.js`); `generate()` has the commit message written. After a commit, `offer` turns the Commit button into Push until something else is selected, a message is typed, the branch changes or the push is done.
- `lanes.js`: which column each commit is in and the lines between them. `git.js`: git's arguments and what its output means. Neither touches the app, so both run under `node`: test a change to them there, against a real `git`.
- `ops.js` runs panel writes and receives requests from menus and dialogs. `git-guard.js` supplies the checkout and ref checks that the diff pane's hunk actions also use. Keep both copies identical. `below()` and `around()` find repositories under and around a folder. `hub.js` reads pull requests, workflow runs and releases via `gh`.
- `write.js`: the commit message writer. `WRITERS` is who can write and with which model; `gather()` reads the change and the earlier messages; `prompt()` is what is asked; `write()` runs `claude -p` or `codex exec`; `clean()` and `wrap()` make the answer a message. Only `write()` and `gather()` need the app: the rest runs under `node`.
- `review-base.js` draws both branch pickers. The switch picker shows the current branch first, then local and remote refs ordered by tip date. Both pickers filter by name and show tip subjects and tracking counts. The base picker prioritizes `main` and `master` as before.
- `menu.js`: the right-click menus. `naming.js`: the name of a new branch or tag. `confirm.js`: the question before a delete, a drop or a discard. The mod opens itself for these, with `props().menu`, `props().naming` or `props().confirm`.
- Props: none in the layout. `{ root, on, view }` pins the folder shown (and the view, `"refs"`), whatever pane has the focus: for a test window.
- State: the view, the folded sections, the repository chosen for a folder (`choice`: `{ folder's key: top folder }`), who writes messages (`writer`) and the lower half's share of the panel's height (`split`, dragged on the line above it with `splitter()`, `drag()`, `drop()`; a double-click clears it), in the copy's `localStorage`. Commit message text is stored in `localStorage.commitDrafts` by machine and resolved worktree root. Draft revisions and generated alternatives are in the panel’s memory. Shared `git-panel.request` holds a request only until the panel takes it.
- `branches`, `fetch`, `pull`, `push`, `refresh` and `write` are available from the command palette. The mouse's back button in Refs goes back to the graph.

## Behavior to preserve

- It never rebases, merges, cherry-picks, resets, forces a push or deletes an unmerged branch (`branch -d`, never `-D`). A pull is `--ff-only`. Those limits are the owner's choice: more is for a terminal.
- A menu or a dialog never runs a program itself: it leaves a request (`ops.request()`), as in `file-explorer`. A request is taken only by the copy that shows its repository (`ops.take(mine)`), so a test window and the panel don't take each other's.
- Before a write, `guard()` checks the checkout and any operation in progress, then verifies the expected branch and refs. Fetch can run during another Git operation. A stash ref names its position in the list, which moves when another stash is made. Every new write gets its `expect`.
- Discard is `git stash push -- <path>`: the changes go to a stash, never away. Keep it that way, or ask the owner. It takes what is staged of the file too, and the dialog says so (`both`). Not `--keep-index`, which looks kinder: that stash can't be applied again over the staged part without a conflict.
- Every git command that is given a path runs with `--literal-pathspecs` (`write()` in `ops.js`, `READ` in `git-diff`): without it a file called `x*` or `foo[1].txt` is a pattern, and staging or discarding it takes other files with it.
- The branch HEAD is on is read with `symbolic-ref HEAD` and cut, never `--short`: that says `heads/main` when a tag is called `main` too, and every check of the branch would fail.
- "Commit all" and "Stage all" are refused while a file is in conflict (`ls-files --unmerged`): a stash applied over other changes leaves conflict marks with no merge under way, and they would be committed.
- Unstage is `git reset -q`, which also works before the first commit.
- The repository shown is the one the pane's folder is in, unless another was chosen for that folder (`choice`), which is part of `key()`: choosing is a change of context, and everything is read again. A chosen one that is gone goes back to the folder's own. A folder in no repository shows the first one under it. A repository that can't be read is not chosen twice (`bad`).
- Repositories are looked for with one `find`, by the `.git` they hold, not deeper than `DEPTH` and never in a home folder, in the folders of installed packages or in `uploads` (`BELOW`, `tooWide()` in `ops.js`): a search of a whole home would take minutes. `DEPTH` is `find`'s, so that of the `.git`: 6 finds a repository five folders down. It was 4, and a project folder that is no repository, with its only ones at `wordpress/wp-content/themes/<name>`, showed "Not a git repository". Without `uploads` left out, 6 takes five seconds in a site with half a million uploaded files; with it, under 50 ms. Time a change to either on the biggest project.
- While a mod pane (the diff, the editor) has the focus, the folder is that of the terminal that had it before, in that tab (`held` in `location()`). With nothing held, since a reload of the mod empties `held` and a tab can come back with its mod pane focused, it is the tab's first terminal's, else the space's first terminal's (`terminalFolder()`). The space's `folder` is the last resort, for a space with no terminal: a space made in one project and moved to another showed the first project's repository.
- Repositories are looked for under the pane's folder only, never from a folder above it. A space's `folder` is where the space was made, not its project (most spaces here have another project's). And the folder above a project holds the other projects: a pane in a folder with no repository would show a stranger's. So a pane in a plain folder with nothing under it says "Not a git repository", also when the folder beside it has one.
- The message writer runs on this Mac, also for a repository on another machine, in the home folder, with no tools (`--tools ""`, `--sandbox read-only`) and no session kept. The diff is in its prompt, fenced and said to be data: it can hold text that reads like an instruction. The prompt is one argument of the program: `DIFF_MOST` and `FILES_MOST` keep it far under what the system allows.
- A writer captures its worktree and draft revision. A later edit keeps its place in the field and exposes **Use generated message** on that worktree. A successful commit clears only the submitted draft if it still matches. The package’s `drafts.test.mjs` exercises a delayed writer across worktrees.
- What a writer answers is only put in the field when the captured draft is unchanged or the user accepts the suggestion. Nothing is committed without the button or Cmd+Enter.
- The message field is a `Textarea`: Enter is a new line, and its `submit` with `secondary` (Cmd+Enter) commits. `on_key_down` around it takes Cmd+Enter too, should the field pass it on. Neither was tried by hand when this was written.
- A name, a path, a message is always an argument of git, never part of a shell script. `PROBE` is the one script, and nothing is put into its text.
- Reads go through `git.READ`: without those flags `git status` refreshes the index, the folder watch sees it, and every read starts the next.
- The log is of `--branches --tags --remotes HEAD`, not `--all`: other tools' refs would show as tips that belong to nothing.
- Other repositories than the one shown are read with `git status` only (`peek()`): every `PEEK_EVERY` and not sooner than ten times as long as the last round took, the first `PEEK_MOST`, `PEEK_AT_ONCE` at a time, only on a tick (on screen, Herdr active). Their log is never read until one is chosen.
- The panel reads only while it is on screen (`shows()`; `visible()` walks `layout()`), at most once a tick, and not sooner than four times as long as the last read took. A copy pinned to a folder (a test window) always counts as on screen: `visible()` finds the layout's copy, not the window, and a window opened while the panel column showed Files read nothing.
- While Herdr is not the active app `tick()` reads nothing and asks GitHub nothing (`away`); the first tick with Herdr active again marks the panel stale and reads at once, still under the four-times back-off. Requests (`act()`, the menu's through `ops.take`) and the commands don't wait for a tick and run while Herdr is inactive: tests driven from a shell rely on that.
- The next page of the log is read by itself when the graph is scrolled to within a screen of its end: on the wheel (`on_scroll_wheel` on the list's container: a scroll area doesn't stop the event) and on the tick (a scrollbar drag says nothing). `loadMore()` asks for one page at a time: not again until a read has brought it (`paged`, set by `history()` from the `limit` its read began with), and nothing once the log was read whole (`more`). The "Load more" row stays, and goes through `loadMore()` too. `nearEnd()` believes the handle only when its height is that of this list: a row is drawn a whole number of the screen's pixels tall, so at a zoom the list is up to a pixel a row longer than `ROW` says (26154 for 1000 rows at 1.3). Tried in a test window driven by "show" requests; the wheel itself was not tried.
- Herdr's `window()` is imported as `app`, here and in `git-diff` and `file-editor`: the global `window` draws the graph (`window.paint_path` in `cell()`), and an import named `window` would hide it.
- A commit's row has its author's initials in a circle before the date (`author()`, `git.initials()`): the name only, never the address, in a color of the theme picked by a number made from the name, so it is the same in every repository. The row for what is not committed has none. The date has a least width (`AGO`), so the circles are one column.
- Each virtual list captures its commit and lane arrays together. Changing projects can request rows from the previous list during a redraw.
- The graph's rows are in a virtual list, so they have no handlers of their own: the list's `on_item_click` and `on_item_secondary_click` do it, by the commit's id. So a name in a row can't be clicked: the Refs view is for that.
- A line of the graph is a shape made once and kept (`path()`): the same few make every row. Making them again on every draw fills the memory all mods share.
- A lane that ends is left empty, never taken out (`lanes.js`): that is what keeps a line passing a row straight.
- A click on a branch in the Refs view stays in that view: its second click must find the same row, to switch. "Show in Graph" is in the menu.
- The switch picker sends the exact ref and expected tip to the panel. When the local branch is already checked out in another worktree, the panel uses **Go to Open Checkout**. For a remote row it looks for a local branch tracking that exact ref. If a local branch of the same name tracks something else, the picker reports the collision.
- The branch picker binds arrows in its specific Input key context because the native field binds them too. Enter uses the field's submit event. Both actions use the refs captured on opening the dialog.
- A hunk write in Git Diff sends `git-panel.index-changed` with the checkout and timestamp. A matching visible panel refreshes so the staged list and commit count follow the index.
- `props()` is read in `init` and kept (`pin`), and `localStorage` is written in `render` (`remember()`): after an `await`, `props()` was seen to answer for another copy, the one that drew last, and the panel reset itself. `localStorage` is treated the same way without having been caught at it.
- A request still marked as running after `BUSY_MOST` is let go: a reload of the mod cuts its task off, and nothing else would clear it.
- GitHub is asked through `gh` on the repository's own machine, and only for reading. No `gh`, no login or no GitHub remote means no marks and no message.
- A failed Actions run opens a keyed window (`failure.js`). It captures the run, repository, machine and checkout in `init`. Only opening the window reads jobs; only selecting a failed job (the first is selected on open) reads its log. The PR badge uses its rollup's check URL, which can identify a different run from the commit's. Other providers open in the browser. The original link remains available on errors. `hub.failedLog()` bounds output at the source, carries the CLI exit status through the pipe, then clips to 160 lines. Results from an earlier job selection are dropped. Log text lives in that window and is copied only by its button or text selection.
- Network commands run under `env GIT_TERMINAL_PROMPT=0`: a prompt for a password would wait for ever. Don't set `GIT_SSH_COMMAND`: it would replace the owner's own.

## Trying it

- **Go to Open Checkout** uses `git.js`’s ref field `checkedOut` to show the branch menu action. On selection, `checkout.js` checks the live terminal folders on the repository’s machine in a single call. Each must be inside a worktree with the same common Git directory and exact local branch. Independent clones, nested repos and detached checkouts stay distinct. Multiple spaces get one row each, and choosing a space repeats the check. The action focuses a matching tab and pane and leaves Git untouched.
- Tested with scratch Git worktrees, symlinks, a nested repository and a separate clone. A simulated Herdr layout covered same-name spaces on different machines, a pane moving during lookup, selecting among several spaces and direct navigation. The branch menu and remote navigation have not been exercised by hand.
- In an isolated Herdr window, the branch picker showed local and remote rows with subjects and tracking counts. A picker request for a branch open in another worktree focused that terminal and kept the originating checkout on its branch. Picker navigation was driven by commands.

- `git-panel` and `git-diff` can be tried on a scratch repository in windows: `openOverlay({ mod: "git-panel", kind: "window", key, width: 380, height: 760, props: { root } })`, and `openOverlay({ mod: "git-diff", kind: "window", key, props: { tab: "probe" } })` with a `git-diff.open` for that `tab`. A request with the scratch `root` in `git-panel.request` is run by that window. How such a window is closed is under Working here in `AGENTS.override.md`.
- `write.js` can be tried under `node` with a stub of `herdr` (`exec`, `home`): a real call costs a little of the owner's usage, so make few.
- `exec` gives a program nothing to read on its input, which `codex exec` needs: with an input left open it waits for it. A test under `node` must close the child's input, or it hangs.
